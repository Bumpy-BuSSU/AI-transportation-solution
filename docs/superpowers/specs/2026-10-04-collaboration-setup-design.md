공동작업 기본 설정 설계
- 날짜: 2026-10-04
- 프로젝트: AI Transportation Solution
- Organization: Bumpy-BuSSU
- Repository: AI-transportation-solution
- 상태: 설계 승인, 구현 전
1. 목적
2인 데이터 분석 프로젝트가 본격적으로 시작되기 전에 필요한 최소한의 공동작업 규칙을 마련한다.
핵심 원칙은 다음과 같다.
- main, dev는 직접 수정하지 않고 PR을 통해 변경 이력을 남긴다.
- 지하철과 따릉이 분석은 서로 독립적으로 진행할 수 있게 한다.
- 상대방 리뷰는 필수가 아니라 필요할 때 요청한다.
- 공통 프로그래밍 언어, 분석 환경, 데이터 형식을 미리 강제하지 않는다.
- 데이터 공유와 자동화 규칙은 실제 필요가 생길 때 확장한다.
이 문서는 기업형 개발 프로세스를 만드는 것이 아니라, 충돌 방지·작업 추적·기여 기록에 필요한 기본 틀만 정하는 것을 목표로 한다.

Organization

- 팀원: Member
Repository

3. 브랜치 구조
기본 흐름은 다음과 같다.
작업 브랜치
    ↓ PR
   dev
    ↓ PR
  main
main
- 최종적으로 안정된 상태를 보관한다.
- 공모전 제출본이나 외부에 보여줄 수 있는 시점을 기준으로 병합한다.
- 직접 push하지 않는다.
- dev에서 PR을 통해서만 병합한다.
dev
- 두 사람의 작업을 모으는 통합 브랜치다.
- 직접 push하지 않는다.
- 각 작업 브랜치에서 PR을 통해 병합한다.
작업 브랜치
작업 단위로 별도 브랜치를 만든다.
권장 형식:
subway/<topic>
bike/<topic>
common/<topic>
docs/<topic>
예:
subway/data-preprocessing
bike/data-cleaning
common/report-structure
docs/update-readme
브랜치 이름은 권장 규칙이며, 핵심은 main과 dev에서 직접 작업하지 않는 것이다.
4. PR 및 병합 규칙
- dev와 main에 들어가는 변경은 PR을 거친다.
- 상대방 리뷰는 필수가 아니다.
- Required approvals는 0으로 둔다.
- PR 작성자가 자신의 PR을 직접 merge할 수 있다.
- 다른 작업 영역에 영향을 주거나 판단이 필요한 변경만 상대방에게 리뷰를 요청한다.
PR에는 최소한 아래 세 가지를 간단히 적는다.
1. 무엇을 변경했는가
2. 왜 변경했는가
3. 어떻게 확인했는가
PR의 목적은 승인 절차보다 변경 이력과 기여 기록을 남기는 것에 가깝다.
5. 작업 영역
초기 담당 영역은 다음과 같이 둔다.
subway/  → 이루
bike/    → 팀원
common/  → 공동
docs/    → 공동
이는 접근 제한이 아니라 주 담당 영역을 의미한다.
필요하면 상대방 영역을 수정할 수 있으며, 이 경우 PR 설명에 변경 이유를 남긴다.
6. Issue 및 Commit 규칙
Issue
작업 추적이 필요한 단위는 GitHub Issue로 관리한다.
예:
- 데이터 전처리 단위
- 분석 단계 추가
- 데이터 품질 문제
- 공통 통합 작업
- 문서 작업
초기 label은 아래 정도만 사용한다.
subway
bike
common
data
docs
bug
필요한 label이 반복적으로 생길 때만 추가한다.
Commit
Commit prefix는 다음 정도로 통일한다.
feat: 기능 또는 분석 기능 추가
data: 데이터 수집·정제·변환·스키마 작업
fix: 오류 수정
test: 검증 및 테스트
docs: 문서 작업
예:
data: normalize subway station names
docs: add collaboration guidelines
fix: handle duplicate dong names
이 규칙은 가독성을 위한 기준이며 자동으로 강제하지 않는다.
7. 데이터 공유 원칙
현재는 지하철 데이터만 구체적으로 정해져 있고, 따릉이 데이터의 종류·크기·라이선스·분석 방식은 아직 확정되지 않았다. 따라서 팀 공통 정책은 최소한으로 둔다.
- Raw 데이터는 기본적으로 Git에 올리지 않는다.
- 분석에 사용한 데이터는 출처와 기준시점을 확인할 수 있어야 한다.
- 라이선스, 개인정보, 재배포 조건, 파일 크기 문제가 있으면 Git에 올리지 않는다.
- Clean/processed 데이터의 업로드 여부는 필요성과 재현성을 보고 작업별로 결정한다.
- 각 작업 영역은 필요하면 공통 기준보다 더 엄격한 데이터 관리 방식을 사용할 수 있다.
예를 들어 지하철 분석에서는 manifest + SHA-256 방식을 사용하더라도 이를 따릉이 분석에 그대로 강제하지 않는다.
두 분석을 실제로 통합해야 하는 시점에만 공통 지역 단위, 시간 단위, 출력 컬럼 등 필요한 최소 인터페이스를 정한다.
8. 분석 및 개발 환경
프로젝트 전체에 하나의 언어와 환경을 강제하지 않는다.
예:
subway/
  requirements.txt   # 지하철 분석에 필요할 경우

bike/
  # 팀원이 선택한 환경
지하철 분석은 Python을 사용할 수 있지만, 팀원은 Python, R, Colab, Notebook 등 자신의 분석에 적합한 도구를 선택할 수 있다.
루트 수준의 공통 의존성 파일이나 공통 실행환경은 실제 공유 코드가 생겼을 때 추가한다.
9. CI 및 자동화
초기에는 공통 CI를 필수로 두지 않는다.
두 분석의 도구와 실행환경이 아직 다를 수 있기 때문이다.
필요하면 각 작업 영역에서 개별적으로 테스트나 CI를 추가할 수 있다. 이후 공통 출력 규격, 공용 스크립트, 최종 통합 검증 등 반복적으로 확인해야 할 항목이 생기면 그때 공통 CI를 도입한다.

11. 초기 세팅 범위
공동작업을 시작하기 전에 아래까지만 설정한다.
1. dev 브랜치 생성
2. main 보호
3. dev 보호
4. 두 브랜치 모두 PR을 통한 병합만 허용
5. Required approvals 0
6. 팀원에게 Repository Admin 권한 부여
7. docs/collaboration.md 작성
8. 최소 README 작성
9. Raw 데이터가 기본적으로 Git에서 제외되는지 확인
현재 단계에서는 다음을 강제하지 않는다.
- 상대방 리뷰
- CODEOWNERS
- 공통 프로그래밍 언어 또는 실행환경
- 루트 수준 Python requirements
- 공통 CI
- 복잡한 Issue/PR template
- Project board / Sprint 관리
- 고정된 데이터 포맷
- 포트폴리오 수준의 공개 문서
12. 완료 기준
다음 조건을 만족하면 초기 공동작업 세팅을 완료한 것으로 본다.
- main, dev에 일반적인 직접 push가 차단되어 있다.
- PR은 상대방 승인 없이 merge할 수 있다.
- 두 사람 모두 작업 브랜치를 만들고 자신의 PR을 병합할 수 있다.
- main과 dev의 역할이 구분되어 있다.
- subway / bike / common / docs 담당 범위가 문서화되어 있다.
- Issue, Commit, 데이터 공유 원칙이 문서화되어 있다.
- 특정 분석 언어나 환경을 팀 전체에 강제하지 않는다.
- README에 프로젝트 주제와 역할 분담이 최소한으로 정리되어 있다.
이후 규칙은 실제 협업 중 문제가 생기거나 공통 요구가 확인될 때만 추가한다.
