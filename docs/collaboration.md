# 협업 규칙

이 문서는 `AI Transportation Solution` 프로젝트의 기본 협업 규칙을 정리한다.  
2인 팀의 작업 충돌을 줄이고 변경 이력과 기여 내용을 확인할 수 있도록 필요한 최소한의 규칙만 둔다.

## 역할 및 작업 영역

- `subway/` — ilwoo-maker
- `bike/` — s-min04
- `common/` — 공동
- `docs/` — 공동

위 구분은 접근 제한이 아니라 주 담당 영역을 의미한다.  
필요하면 상대방의 영역도 수정할 수 있으며, 다른 작업 영역에 영향을 주는 경우 PR에 이유를 남긴다.

## 브랜치 구조

기본 작업 흐름은 다음과 같다.

```text
작업 브랜치
    ↓ PR
   dev
    ↓ PR
  main
```

### `main`

- 최종적으로 안정된 상태를 보관한다.
- 공모전 제출본이나 외부에 공유할 수 있는 시점을 기준으로 병합한다.
- 직접 push하지 않고 `dev`에서 PR을 통해 병합한다.

### `dev`

- 두 사람의 작업을 모으는 통합 브랜치다.
- 직접 push하지 않고 각 작업 브랜치에서 PR을 통해 병합한다.

### 작업 브랜치

작업 단위로 별도 브랜치를 만든다.

권장 형식:

```text
subway/<topic>
bike/<topic>
common/<topic>
docs/<topic>
```

브랜치 이름은 권장 규칙이며, 핵심은 `main`과 `dev`에서 직접 작업하지 않는 것이다.

## PR 및 Merge

- `dev`와 `main`에 들어가는 변경은 PR을 거친다.
- 상대방 리뷰는 필수가 아니다.
- Required approvals는 `0`으로 둔다.
- PR 작성자는 자신의 PR을 직접 merge할 수 있다.
- 다른 작업 영역에 영향을 주거나 별도 판단이 필요한 경우 상대방에게 리뷰를 요청한다.

PR에는 최소한 다음 내용을 적는다.

1. 무엇을 변경했는가
2. 왜 변경했는가
3. 어떻게 확인했는가

PR의 목적은 승인 절차보다는 변경 이력과 기여 내용을 남기는 데 있다.

## Issue 및 Commit

추적할 필요가 있는 작업은 GitHub Issue로 관리한다.

초기 label은 필요한 범위에서 다음을 사용한다.

- `subway`
- `bike`
- `common`
- `data`
- `docs`
- `bug`

필요한 label이 반복적으로 생길 때만 추가한다.

Commit prefix는 다음을 기본으로 사용한다.

- `feat:` 기능 또는 분석 기능 추가
- `data:` 데이터 수집·정제·변환·스키마 작업
- `fix:` 오류 수정
- `test:` 검증 및 테스트
- `docs:` 문서 작업

이 규칙은 가독성을 위한 기준이며 자동으로 강제하지 않는다.

## 데이터 공유

현재 두 분석에서 사용할 데이터의 종류와 관리 방식이 모두 확정된 것은 아니므로 공통 규칙은 최소한으로 둔다.

- Raw 데이터는 기본적으로 Git에 올리지 않는다.
- 분석에 사용한 데이터는 출처와 기준시점을 확인할 수 있어야 한다.
- 라이선스, 개인정보, 재배포 조건, 파일 크기를 고려한다.
- Clean/processed 데이터의 Git 관리 여부는 데이터 특성과 재현 필요성에 따라 작업별로 결정한다.
- 각 분석 영역은 필요하면 더 엄격한 데이터 관리 방식을 사용할 수 있다.

지하철과 따릉이 분석에 공통 데이터 형식을 미리 강제하지 않는다.  
두 분석을 실제로 통합할 필요가 생겼을 때 지역 단위, 시간 단위, 출력 컬럼 등 필요한 최소 기준을 정한다.

## 분석 및 개발 환경

프로젝트 전체에 하나의 프로그래밍 언어나 실행환경을 강제하지 않는다.

각 분석 영역은 목적에 맞는 도구를 독립적으로 선택할 수 있다.

예를 들어 지하철 분석은 Python을 사용할 수 있지만, 따릉이 분석은 Python, R, Colab, Notebook 등 다른 환경을 사용할 수 있다.

공통 의존성, 공통 실행환경, CI는 실제 공유 코드나 반복적인 통합 검증이 필요해질 때 도입한다.

## 운영 원칙

현재는 공동작업을 시작하기 위한 최소한의 틀만 유지한다.

다음 항목은 필요가 생기기 전까지 강제하지 않는다.

- 상대방 리뷰
- CODEOWNERS
- 공통 프로그래밍 언어 또는 실행환경
- 루트 수준의 공통 Python 의존성
- 공통 CI
- 복잡한 Issue/PR template
- Project board 또는 Sprint 관리
- 고정된 데이터 포맷

협업 규칙은 실제 작업 중 반복적인 문제나 공통 요구가 확인될 때 추가하거나 수정한다.
